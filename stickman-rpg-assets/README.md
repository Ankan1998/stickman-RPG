# Stickman RPG — Asset Pack v1.0.0

2D pixel art for a turn-based RPG: **10 hero classes**, **29 enemies**,
**47 weapons**, **43 dungeon tiles** and **16 effects** —
1,071 animation frames in total, across 1,457 PNG files.

Everything here is generated by the Python in `tools/`. There are no hand-drawn
files. If you want to change the art, change the generator and re-run it:

```bash
python tools/build_assets.py out/
```

That keeps the art diffable in git, means a palette change updates every sprite
at once, and means nobody needs a paint program to tweak a colour.

---

## What's in the box

```
characters/heroes/<name>/     frames/*.png, *_<anim>_strip.png, <name>.png, <name>_down.png
characters/enemies/<name>/    same layout
weapons/<name>.png            24x24 inventory icons
dungeon/<name>.png            16x16 tiles and props
fx/<name>/                    32x32 effect frames + <name>_strip.png
atlases/                      packed grids of everything, for engines that prefer one texture
manifest.json                 every asset with its size, frame count, fps and gameplay metadata
tools/                        the generators
```

## The two settings that make pixel art look right

**1. Nearest-neighbour filtering.** In Godot's `project.godot`:

```ini
[rendering]
textures/canvas_textures/default_texture_filter=0
```

Without this the engine interpolates when scaling up and every sprite becomes a
blurry smear. This is *the* classic "why does my pixel art look bad" problem,
and this one line is the whole fix.

**2. Integer scaling.** Characters are 32x40, meant for 3x. Tiles are 16x16,
meant for 3x or 4x. Non-integer scaling makes some pixels bigger than others,
which looks subtly wrong even when you can't say why.

## Conventions

| | |
|---|---|
| Character cell | 32 x 40, standing on the bottom edge, horizontally centred |
| Weapon icon | 24 x 24, optically centred |
| Dungeon tile | 16 x 16 |
| Effect | 32 x 32, 6 frames |
| Animations | idle (4f), walk (6f), attack (6f), hurt (3f), death (6f) |
| Suggested fps | idle 6, walk 10, attack 12, hurt 14, death 8 (death does not loop) |

Every frame of a character is auto-fitted with **one shared crop** across all of
its animations, so a sprite never jitters when it changes state.

## Dropping into the existing game

`characters/*/<name>/<name>.png` and `<name>_down.png` follow the naming the
project's `ActorView` already loads, so the fastest path is:

```bash
cp characters/heroes/*/[a-z]*.png game/assets/
cp characters/enemies/*/[a-z]*.png game/assets/
```

Then add a case in `ContentDatabase.SpriteNameFor` for each new actor. To use
the animations instead of the stills, load `<name>_<anim>_strip.png` as an
`AtlasTexture` / `SpriteFrames` with the frame width of 32.

## Procedural dungeons

Floors and walls marked `seamless: true` in `manifest.json` tile without visible
seams, so a generator can stamp them on a grid directly. The set is built around
the usual room-and-corridor loop:

- **floor** (9): `floor_stone`, `floor_cracked`, `floor_mossy`, `floor_wood`, `floor_sand`, `floor_dirt`, `floor_blood`, `floor_water`, `floor_lava`
- **wall** (6): `wall_stone`, `wall_stone_top`, `wall_cracked`, `wall_mossy`, `wall_brick`, `wall_rune`
- **structure** (8): `door_closed`, `door_open`, `portcullis`, `stairs_down`, `stairs_up`, `pillar`, `arch`, `pit`
- **prop** (17): `chest_closed`, `chest_open`, `barrel`, `crate`, `urn`, `torch_wall`, `brazier`, `bones`, `skull_pile`, `cobweb`, `spike_trap`, `pressure_plate`, `altar`, `rubble`, `banner`, `chain`, `mushrooms`
- **pickup** (3): `key_item`, `coin_pile`, `potion`

`wall_stone_top` is the lit cap for the top row of a wall run; `wall_rune` and
`wall_cracked` are the "something is here" variants worth scattering sparsely.

the same code at a different angle — they can never disagree.
