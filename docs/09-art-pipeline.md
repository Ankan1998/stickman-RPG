# 9. The art pipeline

Every image in this game is **generated by a Python script**. There are no
hand-drawn files, and you do not need a paint program to change anything.

```bash
python tools/make_art.py
```

That writes 24 PNGs into `game/assets/`. Preview them as ASCII in the terminal
without opening anything:

```bash
python tools/make_art.py --preview
```

---

## Why generate the art?

Honest answer: because it makes the art *editable by a programmer*.

| Hand-drawn PNGs | Generated PNGs |
|---|---|
| Binary blobs in git — no meaningful diff | The source is code; `git diff` shows what changed |
| "Make every goblin 10% greener" = redraw them | Change one constant |
| Needs a paint program and the skill to use it | Needs a text editor |
| The palette drifts as you add sprites | One palette, shared by every asset **and the UI** |

It has real limits — you will not draw an expressive character this way, and a
real artist with Aseprite will beat it every time. But for placeholder art that
looks *deliberate* rather than programmer-ugly, it is very hard to beat, and it
means the art never blocks the mechanics work.

## The two files

### `tools/pixelart.py` — the toolkit

A PNG writer and a drawing canvas, in about 250 lines with no dependencies.

**Writing a PNG by hand** turns out to be simple: a signature, a header chunk, a
zlib-compressed block of pixel rows, an end chunk. That is `write_png()`. It
means this repo needs no Pillow, no ImageMagick, nothing.

**The canvas** gives you the primitives you would expect:

| Call | Draws |
|---|---|
| `rect(x, y, w, h, colour)` | filled rectangle |
| `frame(x, y, w, h, colour)` | 1px outline |
| `line(x0, y0, x1, y1, colour, thickness)` | Bresenham line |
| `disc(cx, cy, r, colour)` | filled circle |
| `ellipse(cx, cy, rx, ry, colour)` | filled ellipse |
| `blend(x, y, colour)` | alpha-composite one pixel |

And three post-processing passes that do most of the actual work:

**`outline(colour)`** — adds a 1px dark border around every opaque shape. This
single step is what makes pixel art read clearly against any background. Without
it, sprites look like coloured blobs.

**`shade(light, dark)`** — brightens the top edge of each shape and darkens the
bottom. Gives flat colour a sense of volume, for free.

**`desaturated()` / `rotated_cw()`** — used together to generate every
`*_down.png` (the toppled, greyed-out defeated sprite) automatically from the
living one. Eight sprites for the price of four.

### `tools/make_art.py` — the art itself

One function per asset. A character is built from primitives and then finished:

```python
def warrior():
    c = Canvas(32, 40)

    c.rect(23, 6, 2, 15, STEEL)          # sword blade
    c.rect(21, 20, 6, 2, GOLD)           # crossguard

    c.disc(14, 10, 5, SKIN)              # head
    c.rect(9, 4, 11, 4, STEEL)           # helmet

    c.rect(11, 16, 8, 10, HERO_BLUE)     # torso
    c.line(11, 18, 7, 23, SKIN, 2)       # shield arm
    c.ellipse(6, 25, 4, 5, WOOD)         # shield

    c.line(13, 26, 12, 35, HERO_BLUE_D, 3)   # legs
    c.line(17, 26, 19, 35, HERO_BLUE_D, 3)

    return _finish(c)                    # shade, then outline
```

That is the whole Stick Warrior. Read it top to bottom and you can see the figure
being assembled.

## What gets produced

| Asset | Size | Notes |
|---|---|---|
| `warrior/medic/archer` | 32x40 | Your party |
| `goblin/brute/shaman/warchief` | 32x40 | The enemy |
| `*_down` versions | 40x32 | Auto-generated: rotated and drained of colour |
| `icon_poison/stun/guard/weak/rally/crit` | 16x16 | Status icons |
| `ui_panel`, `ui_panel_dark` | 24x24 | Nine-slice panel backgrounds |
| `ui_button` + hover/pressed/disabled | 24x24 | Nine-slice buttons |
| `bg_arena` | 320x180 | The dungeon backdrop, scaled 4x to 1280x720 |

Sprites are drawn at **32x40** and displayed at **3x**. Keeping the source small
forces clear, readable shapes — you cannot hide behind detail at that size.

## The two settings that make pixel art look right

**1. Nearest-neighbour filtering.** In `game/project.godot`:

```ini
[rendering]
textures/canvas_textures/default_texture_filter=0
```

Without this, Godot smoothly interpolates when scaling up and every sprite
becomes a blurry smear. This is *the* classic "why does my pixel art look bad"
problem, and this one line is the entire fix.

**2. Integer scaling.** The background is 320x180 shown at 1280x720 — exactly 4x.
Sprites are 32x40 at 3x. Non-integer scaling makes some pixels bigger than
others, which looks subtly wrong even when you cannot say why.

## Changing the art

**Recolour the whole game:** edit the palette block at the top of `make_art.py`
and re-run. Every sprite, icon and panel updates together.

```python
HERO_BLUE  = C("4d8fd6")
GOB_GREEN  = C("7dae4c")
```

Then match `UiTheme.cs`, whose palette is deliberately the same colours, so the
interface and the world stay in one visual family.

**Add a new monster sprite:**

1. Write a `def myMonster():` in `make_art.py` returning `_finish(c)`.
2. Add it to the `SPRITES` dict.
3. Re-run the script.
4. Add a case in `ContentDatabase.SpriteNameFor`.

**Replace it all with real art:** drop your own PNGs into `game/assets/` using
the same filenames and delete the generator. Nothing else changes — `ActorView`
just loads `{name}.png`.

## Two lessons the background taught me

Both are visible in the git history of `make_art.py`.

**Gradients must actually be gradients.** The first torch light was three
translucent discs stacked on top of each other. At 4x scale each became a 160px
circle with a *hard visible edge*, so the wall had two enormous brown blobs on
it. Replacing them with a per-pixel quadratic falloff fixed it instantly.

**Translucent things read as grey.** The first flame was semi-transparent orange
discs, which blended with the dark wall into a colourless smudge. Fire has to be
drawn **opaque**, in layers, from dark orange out to near-white at the core.

## Seeing your changes

You cannot unit-test whether a screen looks good. So there is a small screenshot
harness in `GameRoot.cs`:

```bash
godot --path game -- --shots
```

It walks the title, battle and results screens, saves a PNG of each, prints where
it put them, and quits. It reaches the results screen by **simulating an entire
run in a few lines of code** — no clicking, no waiting — which is only possible
because the rules do not need the engine.

That harness is how every screenshot in this project was checked, and how the two
background bugs above were caught.
